## Create an installation

The fastest path is the CLI. It creates a project that depends on `@headless-lms/server`, owns its config and plugins, and deploys anywhere Node and Postgres run.

```bash
npm create headless-lms
```

## Run the repo locally

To develop against the source, you'll need **Node ≥ 22**, **pnpm 10**, and **Docker**. The following brings up Postgres, MinIO and Hatchet, applies migrations, and starts the api, admin and student apps.

```bash
pnpm install
docker compose -f docker/docker-compose.yml up -d   # Postgres, MinIO, Hatchet
cp .env.example .env        # set BETTER_AUTH_SECRET and CREDENTIAL_STORE_KEY
                            # (openssl rand -base64 32 for each)
pnpm db:generate && pnpm db:migrate
pnpm dev                    # api :8000 · admin :8001 · student :8002
```

`.env.example` documents every variable and the command that mints a Hatchet token for the local `hatchet` container.

Sign up in the admin at `http://localhost:8001` and create an organization, then open the student app at `http://localhost:8002`.

### Files

| Variable                 | Required | Default     | Notes                                                                                                                                                                                                      |
| ------------------------ | -------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DELIVERY_URL_EXPIRY`    | no       | `21600`     | Lifetime of a signed file URL, in seconds, from the read that returns it. Must be a positive integer; the API does not start otherwise.                                                                    |
| `MEMBER_IMAGE_MAX_BYTES` | no       | `10485760`  | The largest image a member may upload (profile photo, post cover, message attachment), in bytes. Checked when the upload is finalized. Must be a positive integer; the API does not start otherwise.       |
| `MEMBER_FILE_MAX_BYTES`  | no       | `104857600` | The largest file other than an image a member may upload (a file, video or audio in a post), in bytes. Checked when the upload is finalized. Must be a positive integer; the API does not start otherwise. |
| `REQUEST_LOGGING`        | no       | `true`      | One log line per request with its id, status and duration. Set to `false` to turn the access log off. Refused requests and errors are logged either way.                                                   |

These commands run across all workspaces:

- `pnpm build` · `pnpm test` · `pnpm lint` · `pnpm typecheck`
- `pnpm gen:sdk` regenerates the OpenAPI spec and SDK (the database must be running).

### Apps and domains

An app is a frontend an organization runs on a domain. It serves courses, the community, or both. An organization has at most one app that serves courses and one that serves the community, and a domain belongs to one app across the whole installation. Links the API writes, in emails, member invites and event calendar files, use the domain of the app that serves what the link is about: courses and downloads open the course app, communities and events the community app.

| Variable        | Required | Default                 | Notes                                                                                                                                                                                                 |
| --------------- | -------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PLATFORM_HOST` | no       | `http://localhost:8002` | The origin a new organization's first app starts at, where the student app is: scheme, domain and optional port, with no path. Must be an `http` or `https` origin; the API does not start otherwise. |

A new organization starts with one app that serves both, with the organization's name and slug, at `PLATFORM_HOST`. An installation with one organization needs nothing more: with `PLATFORM_HOST=https://learn.school.com`, the school's app is at `https://learn.school.com`.

When another app already has that address, the organization starts at its slug as a subdomain of it. So does every organization of an installation with a [platform key](/docs/api-keys#the-platform-key). With `PLATFORM_HOST=https://example.com`, a second organization with the slug `acme` starts at `https://acme.example.com`. Creating it answers `409` when another app already has that domain, or when it is the admin app's address or the API's: with the admin app at `https://admin.example.com`, the slug `admin` is refused.

An organization manages its apps in **Settings → Apps**, or under [`/api/apps`](/docs/api/apps/listApps): it adds an app when it moves its community to a separate domain, changes an app's domain when it connects its own, and deletes an app it no longer runs. The next link uses the new domain. Changing the organization's slug later does not change its apps.

For example, Acme starts at `https://acme.example.com` for both. It changes that app to serve courses at `https://learn.acme.com` and adds a community app at `https://club.acme.com`. From then on an email about a completed course links to the first and an email about a new post to the second.

#### Serving a domain

Point each domain at the frontend that serves it, and have that frontend forward `/api` to the API. The browser then calls the API on the domain it is on, and the session cookie belongs to that domain.

The student app does this itself. One deployment serves every organization's course domain, with no setting per organization:

| Variable  | Required | Default                 | Notes                                                                                |
| --------- | -------- | ----------------------- | ------------------------------------------------------------------------------------ |
| `API_URL` | no       | `http://localhost:8000` | Where the student app's server reaches the API. It forwards `/api` there, unchanged. |

- It asks the API which organization its domain is, with [`GET /api/app`](/docs/api/apps/getApp), and shows that organization's name on its sign-in pages.
- It answers `404` on a domain that is no app's, or whose app does not serve courses.
- It keeps the answer for a domain for a minute, so a change to an organization's apps shows in the student app within that minute. Sign-in and every API request follow the change at once.
- It has pages to sign in, ask for a password reset, set the new password and ask for a sign-in link.

Locally, with the defaults, the first organization is at `http://localhost:8002` and a second one with the slug `acme` at `http://acme.localhost:8002`.

#### Signing in on a domain

People sign in on an app's domain: the API trusts the domain of every app, beside the origins in `CLIENT_ORIGIN`, and a change of domain applies from the next request.

- A session started on an app's domain is for that app's organization.
- A person who holds an open invite to that organization gets a session with no organization; accepting the invite sets it.
- Anyone else is refused there, whatever other organization they are in.
- On any other origin, such as the admin app, a person in exactly one organization gets a session for it.
- A session for another organization is answered `401` on an app's domain.
- A password reset link or sign-in link that returns to an app's domain is sent only to a person who is active in that app's organization. The link opens at that domain under `/api`, so the cookie of a sign-in link belongs to the domain the person lands on.

| Variable             | Required | Default | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| -------------------- | -------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AUTH_COOKIE_DOMAIN` | no       | unset   | The parent domain the session cookie is shared across, such as `.example.com`, for an admin app and an API on separate hosts under it. Unset, the cookie is host-only: it belongs to whichever host served the request. Set, an app on a domain under it shares the cookie with every other organization there, and a person who opens another organization's domain signs in again; an app on a domain outside it, such as `learn.acme.com`, gets a host-only cookie. |

## Behind a proxy

The sign-in rate limits and the limit on [`GET /api/app`](/docs/api/apps/getApp) count requests per client IP, read from `X-Forwarded-For`. With more than one proxy in front of the API, such as a CDN and a load balancer, that header holds a chain of addresses, and the API can't tell which one is the client until it knows which are the proxies. Until then every request through the chain counts as one client, and all members share one sign-in limit.

| Variable                  | Required | Default           | Notes                                                                                                                                                                            |
| ------------------------- | -------- | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AUTH_TRUSTED_PROXIES`    | no       | none              | Comma-separated IPs or CIDR ranges of the proxies, e.g. `10.0.0.0/16,192.0.2.10`. The client IP is the first address in the chain, read from the right, that is not one of them. |
| `AUTH_IP_ADDRESS_HEADERS` | no       | `x-forwarded-for` | Comma-separated headers read for the client IP, in order. Name a header only when a proxy sets it itself and drops any copy the client sent.                                     |

List the proxies' own addresses, not a range that also covers clients. The API must be reachable only through these proxies: a client that reaches it directly can send any forwarded header it likes. An installation that builds its own config sets `trustedProxies` and `ipAddressHeaders` on the container config.

A frontend that forwards `/api` to the API is in front of it too. The student app passes on the `X-Forwarded-For` it received, on the calls it forwards and on the calls its own server makes, or the address of the connection when it received none. Run it behind a proxy that sets the header itself, or a client can name any address.

## Live chat

Members see new chat messages, edits, reactions, read marks and typing without reloading. Each browser holds one server-sent event stream to the API, and every API instance receives every chat change through the `PubSub` adapter. Live chat needs it on every instance, a single instance included; `apps/api` wires [`@headless-lms/adapter-pubsub-postgres`](/docs/adapters/pubsub/postgres). Without it the stream route answers 503.

| Variable              | Required | Default        | Notes                                                                                                                                        |
| --------------------- | -------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `PUBSUB_DATABASE_URL` | no       | `DATABASE_URL` | The Postgres the adapter listens on. `LISTEN` needs a session connection: behind a transaction-mode pooler, point this at Postgres directly. |

The stream is `GET /api/member/communities/:communityId/chats/events`. In front of the API:

- **Serve the API over HTTP/2.** Over HTTP/1.1 a browser opens at most six connections per origin across all its tabs, and each open tab's stream holds one, so a sixth tab starves every other request to the API.
- **Don't buffer the stream route.** The API sends `X-Accel-Buffering: no` and `Cache-Control: no-cache, no-transform`; a proxy that buffers responses must not hold back this route's.
- **Keep idle timeouts above 25 s.** The API writes a heartbeat comment on every stream every 25 s, which stays under the common 60 s proxy idle timeout. A shorter timeout drops streams between heartbeats.

On shutdown the API sends every open stream a `closed` event before it stops, and clients reconnect to another instance.
