## Create an installation

The fastest path is the CLI. It creates a project that depends on `@headless-lms/server`, owns its config and plugins, and deploys anywhere Node and Postgres run.

```bash
npm create headless-lms
```

## Run the repo locally

To develop against the source, you'll need **Node ≥ 22**, **pnpm 10**, and **Docker**. The following brings up Postgres, MinIO and Hatchet, applies migrations, and starts the api, admin and student apps.

```bash
pnpm install
docker compose -f docker/docker-compose.yml up -d   # Postgres, MinIO, Hatchet
cp .env.example .env        # set BETTER_AUTH_SECRET and CREDENTIAL_STORE_KEY
                            # (openssl rand -base64 32 for each)
pnpm db:generate && pnpm db:migrate
pnpm dev                    # api :8000 · admin :8001 · student :8002
```

`.env.example` documents every variable and the command that mints a Hatchet token for the local `hatchet` container.

### Files

| Variable                 | Required | Default     | Notes                                                                                                                                                                                                      |
| ------------------------ | -------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DELIVERY_URL_EXPIRY`    | no       | `21600`     | Lifetime of a signed file URL, in seconds, from the read that returns it. Must be a positive integer; the API does not start otherwise.                                                                    |
| `MEMBER_IMAGE_MAX_BYTES` | no       | `10485760`  | The largest image a member may upload (profile photo, post cover, message attachment), in bytes. Checked when the upload is finalized. Must be a positive integer; the API does not start otherwise.       |
| `MEMBER_FILE_MAX_BYTES`  | no       | `104857600` | The largest file other than an image a member may upload (a file, video or audio in a post), in bytes. Checked when the upload is finalized. Must be a positive integer; the API does not start otherwise. |
| `REQUEST_LOGGING`        | no       | `true`      | One log line per request with its id, status and duration. Set to `false` to turn the access log off. Refused requests and errors are logged either way.                                                   |

These commands run across all workspaces:

- `pnpm build` · `pnpm test` · `pnpm lint` · `pnpm typecheck`
- `pnpm gen:sdk` regenerates the OpenAPI spec and SDK (the database must be running).

### Hosts

Every organization holds two hosts: where its course app is reached and where its community app is reached. Links the API writes, in emails, member invites and event calendar files, use them. Links to courses and downloads use the course host; links to communities and events use the community host.

| Variable        | Required | Default                 | Notes                                                                                                                                                                            |
| --------------- | -------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PLATFORM_HOST` | no       | `http://localhost:8002` | The origin a new organization's first host is made under: scheme, domain and optional port, with no path. Must be an `http` or `https` origin; the API does not start otherwise. |

A new organization starts with one host for both apps: its slug as a subdomain of `PLATFORM_HOST`. With `PLATFORM_HOST=https://example.com`, an organization with the slug `acme` starts at `https://acme.example.com`. Slugs are unique, so no two organizations start at the same host. The organization carries its `hosts` wherever it is returned.

An organization changes its hosts by sending `hosts` to [`PATCH /api/organizations`](/docs/api/organizations/updateOrganization), for example when it connects its own domain or moves its community to a separate one. Both hosts are always set, and the next link uses the new value. Changing the slug later does not change the hosts.

People can sign in from a page on any organization's host: the API trusts an origin that is one of an organization's hosts, beside the origins in `CLIENT_ORIGIN`, and a change of hosts applies from the next request. A password reset link or magic link that returns to an organization's host is sent only to a person who is active in that organization. A browser that calls the API from another origin still needs that origin in `CLIENT_ORIGIN`.

| Variable             | Required | Default | Notes                                                                                                                                                                                                                                                                            |
| -------------------- | -------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AUTH_COOKIE_DOMAIN` | no       | unset   | The parent domain the session cookie is shared across, such as `.example.com`. Unset, the cookie is host-only: it belongs to whichever host served the request. Leave it unset when the API is served on each organization's host under `/api`, on domains that share no parent. |

Point each host at the frontend that serves it. An installation with one organization sets `PLATFORM_HOST` to its domain and serves the member app at the organization's host, or stores the address it already uses with the same call.

### Default ports

- `:8000` — API
- `:8001` — Admin dashboard
- `:8002` — Student portal
- `:8005` — Postgres · `:8006/:8007` — MinIO (API / console)
- `:8008/:8009` — Hatchet (gRPC / dashboard)

## Behind a proxy

Sign-in rate limits count requests per client IP, read from `X-Forwarded-For`. With more than one proxy in front of the API, such as a CDN and a load balancer, that header holds a chain of addresses, and the API can't tell which one is the client until it knows which are the proxies. Until then every request through the chain counts as one client, and all members share one sign-in limit.

| Variable                  | Required | Default           | Notes                                                                                                                                                                            |
| ------------------------- | -------- | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AUTH_TRUSTED_PROXIES`    | no       | none              | Comma-separated IPs or CIDR ranges of the proxies, e.g. `10.0.0.0/16,192.0.2.10`. The client IP is the first address in the chain, read from the right, that is not one of them. |
| `AUTH_IP_ADDRESS_HEADERS` | no       | `x-forwarded-for` | Comma-separated headers read for the client IP, in order. Name a header only when a proxy sets it itself and drops any copy the client sent.                                     |

List the proxies' own addresses, not a range that also covers clients. The API must be reachable only through these proxies: a client that reaches it directly can send any forwarded header it likes. An installation that builds its own config sets `trustedProxies` and `ipAddressHeaders` on the container config.

## Live chat

Members see new chat messages, edits, reactions, read marks and typing without reloading. Each browser holds one server-sent event stream to the API, and every API instance receives every chat change through the `PubSub` adapter. Live chat needs it on every instance, a single instance included; `apps/api` wires [`@headless-lms/adapter-pubsub-postgres`](/docs/adapters/pubsub/postgres). Without it the stream route answers 503.

| Variable              | Required | Default        | Notes                                                                                                                                        |
| --------------------- | -------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `PUBSUB_DATABASE_URL` | no       | `DATABASE_URL` | The Postgres the adapter listens on. `LISTEN` needs a session connection: behind a transaction-mode pooler, point this at Postgres directly. |

The stream is `GET /api/member/communities/:communityId/chats/events`. In front of the API:

- **Serve the API over HTTP/2.** Over HTTP/1.1 a browser opens at most six connections per origin across all its tabs, and each open tab's stream holds one, so a sixth tab starves every other request to the API.
- **Don't buffer the stream route.** The API sends `X-Accel-Buffering: no` and `Cache-Control: no-cache, no-transform`; a proxy that buffers responses must not hold back this route's.
- **Keep idle timeouts above 25 s.** The API writes a heartbeat comment on every stream every 25 s, which stays under the common 60 s proxy idle timeout. A shorter timeout drops streams between heartbeats.

On shutdown the API sends every open stream a `closed` event before it stops, and clients reconnect to another instance.
