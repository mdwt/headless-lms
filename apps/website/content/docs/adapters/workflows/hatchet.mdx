`@headless-lms/adapter-workflow-hatchet` implements the `AutomationEngine` and `Scheduler` ports with [Hatchet](https://hatchet.run), giving dispatched automations, notification deliveries and scheduled jobs durable execution. One object implements both ports.

Without it, the container falls back to the in-process `InlineAutomationEngine`: automations and deliveries run immediately in the API process, with one attempt and no recovery if the process dies mid-run, and scheduled jobs are in-process timers that a restart loses. That's fine for development; use Hatchet in production.

A third-party workflow adapter must implement `Scheduler` as well as `AutomationEngine` — `registerJobs`, `at` and `cancel` beside `deliver` — to fill the `workflows` slot.

## How it runs automations

The adapter declares one workflow, `automation-run`: a durable parent task that iterates the dispatched actions, spawning one child task per action with up to 3 retries. Because children are spawned through Hatchet's durable event log, a crash mid-run resumes after the last completed action instead of restarting the sequence. A child that exhausts its retries stops the sequence, and the run is finalized with the results collected so far.

[Webhook](/docs/webhooks) deliveries run through the same workflow: a webhook is an automation whose one action delivers the event, so a failed delivery gets the same retries.

## How it runs notification deliveries

Each email or push of a notification is one `notification-delivery` task with up to 3 retries. A failure on one channel is retried without repeating the others or the in-app notification. The task is keyed by the delivery, so two runs for the same delivery queue instead of overlapping; on the last attempt a failing delivery is marked failed.

## How it runs scheduled jobs

The contexts define timed product work as jobs: publishing a scheduled post at its time, sending a chat's notification once it has been quiet for two minutes, and, every hour, expiring grants, opening due community digests and sweeping unattached uploads. All of them run through one `scheduled-job` task with up to 3 retries, keyed by job and key so two firings of one key queue instead of overlapping.

- A one-off job is a Hatchet scheduled run tagged with the job and its key. Scheduling the same key again moves it; cancelling deletes it.
- A recurring job is a cron named `hlms-job:{job}`. `start()` creates the missing crons, replaces any whose schedule changed and removes those no longer registered.
- A firing whose job has no handler is logged and dropped.

Hatchet keeps the history of every job run. Your org's own scheduled automations keep running on their `automation-schedule` crons.

## Setup

1. Get a Hatchet tenant — [Hatchet Cloud](https://cloud.onhatchet.run) or [self-hosted](https://docs.hatchet.run/self-hosting).
2. Create an API token for the tenant and set `HATCHET_CLIENT_TOKEN`.
3. Inject the adapter.

```ts title="main.ts"
import { HatchetAutomationEngine } from "@headless-lms/adapter-workflow-hatchet";

const container = await createContainer(config, {
  adapters: {
    workflows: process.env.HATCHET_CLIENT_TOKEN
      ? (logger) => new HatchetAutomationEngine(undefined, logger)
      : undefined, // falls back to the inline engine
  },
});
```

The Hatchet SDK reads its own environment — the adapter reads none of it. For tests or non-default setups, pass a pre-built client as the first constructor argument.

## Environment variables

| Variable               | Required | Notes                                                                                 |
| ---------------------- | -------- | ------------------------------------------------------------------------------------- |
| `HATCHET_CLIENT_TOKEN` | yes      | Hatchet API token for the target tenant. Read by the Hatchet SDK, not by the adapter. |

The SDK supports further `HATCHET_CLIENT_*` variables (host/port, TLS, namespace, …) — see the [Hatchet setup docs](https://docs.hatchet.run/home/setup).

## Worker lifecycle

The engine embeds a Hatchet worker in the API process. Your installation's entry point starts it after the server begins listening (`container.automationEngine.start()`); `buildServer` stops it on close. See `apps/api/src/main.ts` for the reference wiring.
