The student app in `apps/student` is one frontend over the member API. Any other frontend uses the same routes, under `/api/member`.

## Sessions and the organization

- A member signs in with email and password through Better Auth (`/api/auth/*`). The session is a cookie.
- The organization comes from the session, not from a header or subdomain.
- Every `/api/member` route answers `401` without a session.

## Access

The API decides what a member can open. A member can open a course, a download or a community when they hold an active grant to it, or to a bundle that contains it. Grants to bundles are resolved on the server; a frontend never sees the difference.

Member routes return only what the member can open and answer `404` for everything else, never `403`, so a response never confirms that something exists. List with [`GET /api/member/courses`](/docs/api/content/listMemberCourses) and [`GET /api/member/downloads`](/docs/api/content/listMemberDownloads), and treat `404` as "not available to this member".

## Showing actions

The server checks every action against the person's permissions. A frontend reads those permissions to show only the actions the person can take, such as moderating a post or opening a draft course:

- [`GET /api/member/viewer`](/docs/api/organizations/getMemberViewer) returns the member's org role, the permissions they hold anywhere, and those they hold on the whole organization.
- [`GET /api/access/permissions`](/docs/api/access/getMyPermissions) adds the permissions they hold on each content item. On one item, a person holds their organization permissions plus that item's.

Decide from permissions, never from a role's key or name. An organization can rename its roles and change what they hold.

## Files

Every file has a stable URL on the API. Each request to it checks access, then answers with a `302` redirect to a signed storage URL. Responses carry these URLs in their file fields, so a frontend puts them straight into `src` or `href` and never asks for a file by asset id.

| File                                    | Field                                                                                                 | Who may fetch it                                                                                                                                                                  |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Course, download or community thumbnail | `thumbnailUrl`                                                                                        | Any org user, when the item is published; a holder of the item's read permission, published or not                                                                                |
| File in a lesson                        | `assetUrls[assetId]` on each activity                                                                 | The member can open the course, the course and lesson are published, and the lesson lists the file; with `courses:read` on the course, published or not, when the lesson lists it |
| File in a download                      | `url` on each file of [`GET /api/member/downloads/{downloadId}`](/docs/api/content/getMemberDownload) | The member can open the download, it is published, and it lists the file; with `downloads:read`, published or not. Saved under its display name                                   |
| Post cover                              | `coverUrl`                                                                                            | Whoever can read the post                                                                                                                                                         |
| Message attachment                      | `url` on each of `attachments`                                                                        | The chat's participants while the message stands; holders of `communities:moderate` while it is flagged                                                                           |
| Profile photo                           | `imageUrl` on authors, senders, directory entries and notifications                                   | Org users of the photo's organization                                                                                                                                             |
| Your own upload                         | `url` on a finalized upload, and `imageUrl` on your own profile                                       | Only the person who uploaded it                                                                                                                                                   |

Anything else is a `404`. The Files section of the [API reference](/docs/api) lists every route.

```tsx
<img src={course.thumbnailUrl} alt="" />
<video src={activity.assetUrls[videoAssetId]} controls />
<a href={file.url} download>
  {file.displayName ?? file.filename}
</a>
```

### The session cookie has to reach the API

An `<img>` or `<video>` request can't carry a token; it sends cookies. Serve the frontend and the API from the same site, as subdomains of one domain such as `learn.example.com` and `api.example.com`, and set `AUTH_COOKIE_DOMAIN` to the parent domain (`.example.com`). Locally everything runs on `localhost`, which already shares the cookie. Don't set `crossorigin="anonymous"` on media elements, since it stops the cookie being sent to another subdomain.

### Link lifetimes

The stable URL never expires; only the storage link it redirects to does. Requesting the stable URL again returns a fresh one.

| File               | Storage link lifetime | Setting                   |
| ------------------ | --------------------- | ------------------------- |
| File in a download | 5 minutes             | `DELIVERY_URL_EXPIRY`     |
| Every other file   | 24 hours              | `STORAGE_DOWNLOAD_EXPIRY` |

A download link is used once to start the download. Video and audio keep fetching parts of the file while they play, so their links outlive a viewing.

## Lesson content

A lesson's content is in its activity's `settings.content`, as `{ type, version, config }`. `config` is in the editor's own format: render it with the editor's `Renderer`, passing the activity's `assetUrls`. See [Custom editor](/docs/editor).

## Live chat

A member's chats update over one server-sent event stream per tab: [`GET /api/member/communities/{communityId}/chats/events`](/docs/api/chats/streamMemberChatEvents). The browser opens it with the session cookie, from an origin the API allows. The SDK exposes it as `Chats.streamMemberChatEvents`, which yields each event with its `type`:

```ts
const { stream } = await Chats.streamMemberChatEvents(
  { communityId },
  { client, credentials: "include", sseMaxRetryAttempts: 0, signal },
);
for await (const event of stream) {
  apply(event);
}
```

The stream never replays what a member missed. A client loads state whenever the stream asks it to, and applies events on top.

### Load state on `ready` and `resync`

1. Open the stream.
2. On `ready`, start buffering events, and load the first page of the inbox ([`listMemberChats`](/docs/api/chats/listMemberChats) with `requests=false`), the pending requests (`requests=true`) and the latest page of the open chat ([`listChatMessages`](/docs/api/chats/listChatMessages)). The `unread` event after `ready` sets the badge.
3. When the loads settle, replace the inbox rows and the requests with them, drop every loaded thread but the open one, merge the open chat's page by message id, and then apply the buffered events in order.
4. While connected, apply events as they arrive.
5. On `resync`, wait a random 0–3 s and repeat steps 2 and 3.

### Events

| Event               | Data                                                        | Apply                                                                                                                                           |
| ------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `ready`             | `heartbeatMs`                                               | Load state                                                                                                                                      |
| `message.created`   | `chatId`, `message`                                         | Insert by id; set the row's last message and move it up. Fetch the row with [`getMemberChat`](/docs/api/chats/getMemberChat) when there is none |
| `message.updated`   | `chatId`, `message`                                         | Replace the message's fields by id                                                                                                              |
| `message.deleted`   | `chatId`, `messageId`, `deletedAt`                          | Mark it deleted and drop its body and images                                                                                                    |
| `message.reactions` | `chatId`, `messageId`, `reactions`, `orgUserId`, `reaction` | Replace the counts; set the viewer's own reaction when `orgUserId` is the viewer                                                                |
| `chat.updated`      | `chatId`, `chat`, `participants`                            | Replace the row's chat and participants, or fetch the row when there is none                                                                    |
| `chat.removed`      | `chatId`                                                    | Drop the row                                                                                                                                    |
| `chat.state`        | `chatId`, `unread`, `lastReadMessageId`, `subscription`     | Set the row's unread count, read mark and mute                                                                                                  |
| `unread`            | `unread`, `requests`                                        | Set the badge                                                                                                                                   |
| `typing`            | `chatId`, `orgUserId`, `until`                              | Show that the participant is typing until `until`                                                                                               |
| `resync`            |                                                             | Load state                                                                                                                                      |
| `closed`            | `reason`: `access`, `session` or `shutdown`                 | The stream has ended                                                                                                                            |

A message in an event has no `viewerReaction`; keep the one already stored. Unread counts come from `chat.state` and `unread`; a client never counts them itself. When a mute lapses, read the total again with [`getMemberChatUnread`](/docs/api/chats/getMemberChatUnread).

### Sending

Give each send a new `clientId` (a UUID) and show the message as pending. Replace it with the returned message, or with the `message.created` whose sender is the viewer and whose `clientId` matches, whichever arrives first. A retry of a failed send reuses its `clientId`, and the API returns the message already stored instead of sending it twice. Call [`sendChatTyping`](/docs/api/chats/sendChatTyping) at most every 3 s while the member types.

### Reconnecting

- On a dropped connection or `closed` with `shutdown`, reconnect after a random 0–5 s; the new stream starts with `ready`. While connects keep failing, back off exponentially with full jitter, from 1 s up to 30 s.
- A `401` or `closed` with `session` means the session ended: send the member to sign in. A `403` or `closed` with `access` means they can no longer open the community.
- With the SDK's own retries off, a refused connect ends the stream without its status. Pass the client a `fetch` that records each response's status, and read it when a stream ends before `ready`.
- When connects keep failing, poll `getMemberChatUnread`, the inbox's first page and the open chat's latest page every 15 s while the tab is visible, one request at a time, and stop once a stream reaches `ready`.
- Close the stream when the tab has been hidden for a while, and reopen it when the tab is visible again.
